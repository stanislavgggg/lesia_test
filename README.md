# Чекап «Характер чи сценарій» — v1.2

Реалізує ТЗ v1.2 від 8 вересня 2026. Деплой — Cloudflare Workers (static assets + власний скрипт).

---

## 1. Деплой

### Чому важливо деплоїти саме через Wrangler

Drag-and-drop у **новому** дашборді Workers («Upload and deploy») будує Worker
**тільки зі статики**, без власного скрипту — і навіть якщо серед завантажених файлів
є `_worker.js`, цей спосіб його не підхоплює як точку входу. Наслідки:

- `/api/checkup/lead` не існує → будь-який сабміт форми падає з «Не вдалося зберегти
  дані», бо запит іде в 404, а не в наш обробник;
- у **Settings → Variables and secrets** дашборд прямо пише: *«Variables cannot be
  added to a Worker that only has static assets»* — додати змінні нізвідки.

Це не налаштування, яке можна десь увімкнути в цьому інтерфейсі — платформа не дає
прикріпити скрипт до вже завантаженої статики заднім числом. Єдиний надійний спосіб
отримати Worker **зі скриптом** (а не тільки статикою) — задеплоїти через Wrangler
з конфігом, який явно вказує на `_worker.js` як `main`.

### Варіант A. Wrangler (рекомендовано, вирішує проблему з Variables)

```bash
npm install                 # разом з тестовими залежностями підтягне wrangler
npx wrangler login          # відкриє браузер, увійти в акаунт Cloudflare
npm run deploy               # збирає public/ і виконує wrangler deploy
```

`npm run deploy` = `npm run build:public && npx wrangler deploy`. Конфіг лежить
у `wrangler.jsonc`: `main: "_worker.js"` + `assets.directory: "./public"`. Саме
поєднання «є `main`» + «є `assets`» — це те, що дашборд визнає повноцінним Worker'ом,
і після цього деплою в **Settings → Variables and secrets** змінні вже можна додавати
(розділ 2 нижче), або одразу через термінал:

```bash
npx wrangler secret put RESEND_API_KEY
npx wrangler secret put TELEGRAM_BOT_TOKEN
# і так для кожної секретної змінної з таблиці в розділі 2
```

Перевірити конфіг без реального деплою: `npx wrangler deploy --dry-run` — вивід має
показати `env.ASSETS → Assets` у списку біндингів.

### Варіант B. Legacy Pages, drag-and-drop (без термінала, без CLI)

Якщо термінал недоступний: у Cloudflare Dashboard на екрані «Create application»
є посилання **«Continue to Pages»** внизу — це старий, окремий продукт Pages
(не плутати з новим «Upload and deploy» для Workers), і **тільки він** підтримує
`_worker.js` через drag-and-drop без CLI.

```bash
npm run dist
```

У `dist/` потрапляє все, що потрібно завантажити: `index.html`, `assets/`, `_worker.js`,
`_headers`, `og.jpg`, `robots.txt`.

1. Cloudflare Dashboard → **Workers & Pages** → **Create application** → **«Continue to Pages»**.
2. Перетягнути **вміст теки `dist/`** → **Deploy site**.
3. Після першого деплою: **Settings → Environment variables** → додати змінні з розділу 2,
   потім **Create a new deployment**, щоб вони підхопилися.

### Локально

```bash
npm run dev   # збирає public/ і піднімає wrangler dev — те саме середовище, що й продакшн
```

## 2. Що обов’язково заповнити перед релізом

### `assets/content.js` → `CONFIG`

| Ключ | Зараз | Що поставити |
|---|---|---|
| `privacyPolicyUrl` | `{{PRIVACY_URL}}` | посилання на чинну Політику конфіденційності |
| `privacyConsentVersion` | `{{PRIVACY_VERSION}}` | версія затвердженого тексту згоди, напр. `pp-2026-09-01` |
| `landingCanonicalUrl` | `https://aleksa.space/checkup` | фінальний canonical |
| `resultCtaUrl` | `https://ig.me/m/aaaleksa.novi` | перевірити на iOS, Android і у вбудованому браузері Instagram |

Те саме значення canonical продублювати в `index.html` **у трьох місцях** (соцмережі й Google
не виконують JS, тому ці теги мають бути статичними, не підставленими скриптом):
`<link rel="canonical" id="canonical-link">`, `<meta property="og:url" id="og-url">` і хост
у `<meta property="og:image" id="og-image">` (лишити абсолютний URL, не відносний `/og.jpg` —
інакше Facebook/Telegram-превʼю не підтягнуть картинку).

**Важливо:** зараз сайт живе на `lesia-test.globalstore24.workers.dev` (workers.dev-домен),
а `aleksa.space` підключений до Cloudflare, але жоден Worker до нього ще не прив'язаний
(*Workers & Pages → Domains → Custom Domains* — порожньо). Поки не буде або (а) прив'язаного
custom domain, або (б) Route `aleksa.space/checkup*` на цей Worker — canonical/og:url
вказуватимуть на адресу, за якою сайт фактично не відкривається. Перед релізом вирішити:
корінь домену чи підшлях `/checkup`, підключити відповідно, і тільки тоді проставляти
фінальні значення тут.

### Змінні оточення Cloudflare Pages

*Settings → Variables and Secrets → Production*

| Змінна | Обов’язково | Призначення |
|---|---|---|
| `RESEND_API_KEY` | для листів | ключ [Resend](https://resend.com) |
| `EMAIL_FROM` | для листів | `Леся Новікова <checkup@домен>` — домен має бути верифікований |
| `EMAIL_REPLY_TO` | ні | адреса для відповіді |
| `CRM_WEBHOOK_URL` | для CRM | куди POST-ити лід |
| `CRM_WEBHOOK_SECRET` | ні | іде заголовком `X-Webhook-Secret` |
| `PRIVACY_VERSION` | так | перекриває версію згоди з клієнта; серверне значення — джерело істини |
| `STORE_SCENARIO` | ні | `true`, лише якщо email-сервіс або Telegram реально потребують `scenarioKey` |
| `TELEGRAM_BOT_TOKEN` | для Telegram-сповіщень | токен бота від [@BotFather](https://t.me/BotFather) |
| `TELEGRAM_CHAT_ID` | для Telegram-сповіщень | куди слати сповіщення про новий лід |

Змінні можна додати або через дашборд (*Settings → Variables and secrets* — з'являється
тільки після деплою через Wrangler, див. розділ 1), або з терміналу:

```bash
npx wrangler secret put TELEGRAM_BOT_TOKEN
npx wrangler secret put TELEGRAM_CHAT_ID
```

**Як отримати `TELEGRAM_BOT_TOKEN`:**

1. Написати [@BotFather](https://t.me/BotFather) в Telegram → `/newbot` → задати ім'я й
   username → у відповідь прийде токен виду `123456789:AAExampleToken`.

**Як отримати `TELEGRAM_CHAT_ID`:**

- Якщо сповіщення мають приходити в особисті — написати своєму щойно створеному боту
  будь-яке повідомлення, потім відкрити
  `https://api.telegram.org/bot<TOKEN>/getUpdates` у браузері й узяти
  `message.chat.id` з відповіді (від'ємне число — це вже груповий чат, теж підходить).
- Або простіше: написати [@userinfobot](https://t.me/userinfobot) — він одразу покаже
  `Id` у відповідь.
- Якщо сповіщення мають приходити в групу — додати бота в групу, написати там будь-що,
  і так само подивитись `getUpdates` (id групи буде від'ємним).

Якщо `TELEGRAM_BOT_TOKEN`/`TELEGRAM_CHAT_ID` не задані — крок просто пропускається,
нічого не ламається.

**KV-біндинг (рекомендовано):** *Settings → Functions → KV namespace bindings* → змінна `LEADS_KV`.
Без нього ідемпотентність працює тільки в межах одного ізоляту — подвійний tap на різних edge-нодах теоретично може створити два ліди.

- `og.jpg` — зараз згенерована службова обкладинка 1200×630 системним шрифтом. **Замінити на фінальну від дизайнера.**

## 2а. Маршрути (URL-структура)

Кожен екран чекапу — окрема адреса, не один "порожній" URL на весь тест:

| URL | Екран |
|---|---|
| `/` | Вступ (+ пропозиція продовжити, якщо є збережений прогрес) |
| `/q/1` … `/q/10` | Питання 1…10 |
| `/form` | Реєстраційна форма (ім'я, email, згоди) |
| `/result` | Результат |
| `/error` | Технічна помилка показу результату |

Це працює через `history.pushState` на клієнті (`assets/app.js`) — сторінка залишається
SPA, окремих HTML-файлів на кожне питання немає. Кнопки "Назад"/"Вперед" браузера
відповідають реальному кроку тесту. Пряме відкриття або оновлення сторінки на `/q/5`,
`/form` чи `/result` теж працює: `_worker.js` віддає для всіх цих шляхів той самий
`index.html`, а застосунок сам розбирає URL і показує потрібний екран (детальніше —
`SPA_ROUTES` у `tools/worker-template.js` і `navigateOnLoad()`/`popstate` у `assets/app.js`).
Маршрути питань, форми й результату позначені `noindex, follow` (розділ 16 ТЗ) — в
пошуковий індекс потрапляє лише `/`.

## 2б. Захист лід-форми від спаму й ботів

Публічний POST-ендпоінт без авторизації — типова ціль для спам-ботів. Реалізовано два
рівні захисту без зовнішніх сервісів (Turnstile/reCAPTCHA не підключені, за потреби —
легко додати окремим кроком у `handleSubmit`):

- **Honeypot-поле** `website` у формі — приховане CSS (`.hp` у `styles.css`), не в
  `display:none`/`hidden`, а офскріном + знятий `tabindex` і `aria-hidden` на обгортці:
  людина й скрінрідер його не бачать і не заповнюють, а боти-автозаповнювачі — часто так.
  Заповнене поле → сервер мовчки повертає фейковий успіх, нічого не зберігаючи і не
  надсилаючи в CRM/лист/Telegram (щоб не підказувати боту, що його розпізнали).
- **Rate limit за IP**: не більше 8 заявок з однієї IP за 10 хвилин (`tools/worker-template.js`,
  `checkRateLimit`). Як і ідемпотентність без KV — це best-effort у межах одного ізоляту,
  не синхронізовано між edge-нодами Cloudflare. Для суворішого ліміту — підключити KV
  або Cloudflare Rate Limiting Rules на рівні зони.

Жоден із цих механізмів не захищає від цілеспрямованого скрипта, який читає публічний
`assets/app.js` і напряму б'є в API, оминаючи сторінку — для такого рівня загрози потрібен
Turnstile. Поточний захист розрахований на типових generic-ботів і масовий спам.

## 3. Структура

```
index.html                     розмітка всіх екранів
assets/content.js              весь контент і конфіг, окремо від UI
assets/scoring.js              алгоритм підрахунку (чистий модуль, без DOM)
assets/app.js                  стан, валідація, навігація, аналітика
assets/styles.css              темна тема, mobile-first, токени станів
_worker.js                     АВТОЗГЕНЕРОВАНО: ендпоінт ліда + роздача статики
_headers                       CSP, Referrer-Policy, X-Frame-Options, кешування
wrangler.jsonc                 конфіг Wrangler: main=_worker.js + assets.directory=./public
tools/worker-template.js       вихідник обробника ліда — правити тут
tools/build-worker.mjs         збирає _worker.js із шаблона та текстів
tools/make-public.mjs          збирає public/ (без _worker.js) для деплою через Wrangler
tools/make-dist.mjs            збирає dist/ (з _worker.js) для drag-and-drop у legacy Pages
tests/scoring.test.mjs         11 юніт-тестів алгоритму
tests/lead-function.test.mjs   19 тестів обробника ліда, роутера (включно з SPA-маршрутами), Telegram-сповіщень, honeypot і rate limit
tests/e2e.mjs                  81 наскрізна перевірка в jsdom
og.jpg, robots.txt, sitemap.xml, package.json
```

> **Важливо.** `_worker.js` генерується. Після правки текстів у `assets/content.js`
> або логіки у `tools/worker-template.js` обов'язково `npm run build` — інакше лист
> піде зі старими формулюваннями. `npm run dist` робить це автоматично.

Тексти питань і результатів **не зашиті в компоненти**. Зміна формулювання без зміни `scale`/`key`
не вимагає правок алгоритму (вимога розділу 17 ТЗ).

## 5. Два місця, де реалізація відходить від букви ТЗ

Обидва потребують підтвердження замовника.

**1. Нічия при рівних балах.** Псевдокод у §6.4 при однакових максимумах нижче 4 балів мовчки
обирає переможця за порядком питань. Правило в §6.3 («При равных максимальных баллах результат
всегда смешанный») цьому суперечить. Реалізовано **правило**, не псевдокод: додана окрема гілка
`tiedAtMax.length >= 2 → mixed`. Кейси T-01…T-04 і T-09 від цього не змінюються.

**2. Індикатор вираженості при кейсі T-02.** Перфекціонізм 8/8 при `overallIntensity = 0.8` дає
`intensityLevel: 'low'`. Показувати під заголовком «Твій сценарій — Перфекціоністка» текст
«сценарії не перехоплюють керування» було б суперечливо. Додано окремий рядок
`INTENSITY.focused` — «Загальний фон спокійний — але цей сценарій виражений».

## 6. Приватність

- В `dataLayer` / GA4 / Pixel **не йдуть**: ім’я, email, тексти й значення відповідей, бали,
  назви сценаріїв. Перевіряється тестом у `tests/e2e.mjs`.
- Відповіді та бали зберігаються **локально** (`localStorage`), на сервер іде мінімальний
  `resultPayload` лише для формування листа.
- У CRM і Telegram-сповіщенні за замовчуванням не пишеться `scenarioKey` — тільки за
  прапорцем `STORE_SCENARIO=true`, і тоді це треба окремо описати в Політиці
  конфіденційності та обмежити строк зберігання.
- Telegram-сповіщення (якщо ввімкнене) і надсилання листа й запис у CRM виконуються у
  фоні через `ctx.waitUntil()` **після** того, як людина вже побачила результат на
  екрані — не блокують і не сповільнюють показ результату.
- Обидві галочки згоди зняті за замовчуванням; маркетингова не блокує доступ до результату.
- CSP у `_headers` забороняє сторонні скрипти. **Підключення GA4 / Meta Pixel вимагає правки
  `script-src` і `connect-src`** — інакше вони мовчки заблокуються.

## 7. Що перевірити руками перед прийманням

- [ ] `ig.me`-посилання відкриває Direct; при невстановленому застосунку з’являється резервне
      посилання на профіль (показується через 1,2 с після кліку).
- [ ] Ширини viewport 320 / 360 / 375 / 390 / 430 / 768 / 1024 / 1440 — без горизонтального скролу.
- [ ] Збільшення тексту браузером до 200%.
- [ ] Клавіатура і screen reader: фокус після «Далі/Назад» переходить на заголовок питання.

- [ ] Вимкнені cookies / недоступний `localStorage` — чекап працює, просто без відновлення сесії.
- [ ] Реальний лист від Resend: тема, прехедер, кнопка CTA, відсутність рекламних блоків
